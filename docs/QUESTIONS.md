## A. 范围与优先级（拷问 PRD）

### Q1 ✅ 弹幕（F-08）真的是 P0 的 M 吗？

- **证据**：红果弹幕接口无独立表情字段、无表情清单接口（4 个候选路径全 404）；guoapp 为此内置 ~55 条对照表 +  
  Go 侧校验/游标/缓存（~300 行）+ Dart overlay + emoji 安全截断（FE0F/FE0E/200D 前回退，真机乱码反馈逼出来的）。  
  整块复杂度约等于半个子系统，且**只有红果一个源受益**（第三方默认不开放该 cap）。
- **选项**：a) 维持 M，整套照抄 EVIDENCE §7 常量；b) 降为"最小闭环"（开关+渲染+分集校验，砍表情/缓存调优）；  
  c) 移出 P0（P1 或永不）。
- **建议**：b。若选 c，PRD F-08 整行删除，EVIDENCE §7 降级为备查。

**✅ 已决（2026-10-14）：暂时不做（比 c 多保留编号）。** F-08 编号保留不复用，PRD 标记暂缓；  
SourceSpec §3.4 与 EVIDENCE §7 冻结备查，P1 恢复则整套照抄。PRD §5、ARCH §3.2/§8/§9 的弹幕条目同步冻结。

### Q2 ✅ "首版只跑通在线播放闭环"和 F-06/F-07（追剧/下载）并列 M，矛盾吗？

- **证据**：guoapp 自己的首版就是纯播放闭环；追剧/下载/合并是 0.2.9~0.2.12 逐版堆的，下载是最硬的契约  
  （.bundle 指纹/.part 续传/ENDLIST 校验，每条背后都是事故）。
- **选项**：a) 维持三合一 M；b) M=播放闭环，追剧/下载降 Should（M1 后即做）；c) 维持但下载砍 HLS 只做 MP4。
- **建议**：b，并把"杀进程不丢进度"（F-06 的核心验收）保留在 M——它只依赖 5s 落盘，不依赖完整追剧状态机。

**✅ 已决（2026-10-14）：a。** 播放闭环+追剧+下载三合一维持 M；"杀进程不丢进度"随 F-06 保留在 M。

### Q3 ✅ 多用户本机隔离，首版就要吗？

- **证据**：guoapp 的多用户是被事故逼出来的（损坏配置回退无密码管理员、偏好保存静默失败、恢复混合态）；  
  代价是 PIN 12 万次迭代、快照提交、profileEpoch 在途作废、备份恢复链路——对一个演示版是纯负担。
- **选项**：a) 首版单用户 + 数据模型预留 `user_id`；b) 首版即完整多用户；c) 首版无用户概念，P1 补。
- **建议**：a。PRD §2 已按此预填（预留维度），若选 b/c 需回改。

**✅ 已决（2026-10-14）：完全移除多用户（比建议的 a 更彻底）。** 单用户全局存储、无 PIN、数据模型不预留 `user_id`、  
管理员设置降级为全局设置；备份损坏恢复简化为可重试+保留原文件。PRD §2/§6、ARCH §3.1/§3.2/§5.1、EVIDENCE §1/§6/§15 已回写。

### Q4 ✅ VIP 三态要不要？

- **证据**：guoapp 的 VIP 三态（未知/免费/VIP、未知不覆盖已知）是为黄豆源做的；我们的官方源首批 2–3 个里  
  是否有 VIP 源未定（PRD §7.2 未关）。
- **选项**：a) 模型预留三态字段，UI 后置；b) 完整照抄（隐藏已确认 VIP+斜线标识）；c) 不做。
- **建议**：a。字段留着不占首版工作量。

**✅ 已决（2026-10-14）：a。** 模型预留三态字段（未知不覆盖已知），UI 后置；PRD §4 已回写。

## B. 契约与架构（拷问 ARCH/SourceSpec）

### Q5 ✅ `play` 让插件直接返回密钥（hlsKey/cencKey）给引擎，沙箱模型下可接受吗？

- **证据**：guoapp 是引擎自己解析所以密钥不出引擎；插件化后密钥必须过插件内存——这是 WASM 化的固有代价。  
  备选：插件只回 URL+格式，密钥由 host 函数按 URL 代取（凭证不离开引擎）。
- **选项**：a) 插件返回密钥（EVIDENCE §3.1 已预填）；b) host 代取模式；c) 两者并存，manifest 声明。
- **建议**：c 太重；先 a（第三方源少、密钥短命），把 b 记为 v2 演进。**注意**：无论哪种，密钥都不进备份/同步/日志。

**✅ 已决（2026-10-14）：先 a，b 记为 v2 演进。** 插件返回密钥为 v1 正式契约；host 代取（凭证不出引擎）记 v2，  
manifest 不开双模式声明位；密钥不进备份/同步/日志为硬约束。SourceSpec §3.1 已回写。

### Q6 ✅ 限流/退避的权威在哪一侧？

- **证据**：SourceSpec v0.1 两头都写（插件配额 + 引擎 limiter）——插件各自为政正是 guoapp per-source UA 混乱  
  （iPhone/Chrome131/okhttp 三套并存）的根因。
- **选项**：a) 引擎唯一权威，插件配额只做 trap 保护（已预填）；b) 插件自治。
- **建议**：a，无悬念。真正要决的是**引擎 limiter 的默认值**（并发 3/间隔 250ms 是否适合我们的源规模）。

**✅ 已决（2026-10-14）：a。** 引擎唯一权威；插件配额只做 trap 保护。limiter 默认值（并发 3/间隔 250ms）  
留 M1 用红果+首批官方源实测校准。

### Q7 ✅ 取消协议：Rust+tokio 下还要 (session, sequence) 仲裁吗？

- **证据**：guoapp 的仲裁是为"Go 单例 + 每次现开 isolate + 迟到响应"设计的；Rust 常驻 worker 下  
  sequence 仍要（防迟到响应），但 session GC/在途上限可以简化。
- **选项**：a) 照抄后简化；b) 用请求 ID + generation 令牌重设计；c) 不取消，只超时丢弃。
- **建议**：a。**超时后补发取消**这条必须留（否则在途请求泄漏，guoapp 踩过）。

**✅ 已决（2026-10-14）：a 起步，b 作为 P1 引擎演进项。** session/sequence 仲裁与超时补发 cancelRead 保留；  
GC/在途上限简化为单用户常量；请求 ID+generation 重设计记 P1。ARCH §3.2 已回写。

### Q8 ✅ TLS 指纹做不到，皮果类源直接放弃？

- **证据**：guoapp 20 源只有 2 类需要 Chrome 指纹（tls-client Chrome_150），且皮果仍被 CF 拦（README 自认  
  "当前实现不做规避"）。reqwest 无此能力；rquest 未评估（工作量+供应链审计）。
- **选项**：a) P0 不做指纹，该类源报 WAF_BLOCK；b) 评估 rquest 并按 host 白名单启用；c) 内置浏览器 WebView 取流。
- **建议**：a 起步（官方源首批可控，绕开需要指纹的源），b 作为 P1 引擎演进项。**c 不要**——包体/复杂度/合规都疼。

**✅ 已决（2026-10-14）：a 起步，b 作为 P1 引擎演进项。** P0 不做指纹，需要指纹的源报 `WAF_BLOCK`，  
官方源首批签约绕开；rquest 评估记 P1；c（WebView 取流）明确不做。PRD §4、ARCH §2、SourceSpec §5 已回写。

## C. 平台与分发（拷问 PRD §3/§7）

### Q9 ✅ "iOS 液态玻璃风格"在 Windows 上实际是 standard 视觉，设计验收按哪档？

- **证据**：Windows Skia/ANGLE 下 `isShaderFilterSupported=false`，premium 静默走 lightweight（standard 视觉）；  
  不开 adaptive 也是如此。若追求 premium 视觉，Windows 需要切 Impeller-ANGLE——未验证，且 glass 包 Phase 1 仍钳 standard。
- **选项**：a) 按 standard 验收（已预填）；b) Windows 试 Impeller-ANGLE 冲 premium；c) macOS 独占 premium 视觉、其他平台标准。
- **建议**：a，并在设计评审时明确"三端视觉分档"是验收前提，避免后期扯皮。

**✅ 已决（2026-10-14）：Flutter 升级最新稳定版，采用 Impeller——但基线以 media_kit 兼容为准。** 同日修订为  
**3.47.4 / Dart 3.13.3**：guoapp 用 `media_kit 1.2.6 + video 2.0.1 + libs_video ^1.0.7`（与本项目计划同款）在其 CI 四处 pin `3.47.4`  
并完成编译验证（`pubspec.yaml:15-17`、`.github/workflows/build.yml:35,76,124,171`、`README.md:730,993`），  
故"media_kit 兼容的最新稳定版"= **3.47.4**，而非拍脑袋的 3.47.6。

- **3.47.6**（2026-10-01 同线 hotfix，Dart 3.13.5）待 M0 冒烟后小步跟进，不追 3.50；
- **降级路径**：M0 真机播放 spike 不通过则降到 **3.38.10 / Dart 3.10.8**（media_kit 1.2.2 changelog 明确 "feat: flutter 3.38.x support"）；降级后桌面默认回 Skia，Windows/Linux 需手动开 Impeller，wide gamut 不再默认，Windows premium 实验取消——验收档位结论不变（Win/Linux 仍 standard）。
- 渲染事实（已核实）：Win/Linux 后端 = GLES via ANGLE→D3D11（**非 Vulkan**）；macOS Metal；macOS 最低升 12 / iOS 最低升 15。
- **三端视觉分档验收（per-platform maxQuality）**：macOS premium / Windows+Linux standard / Android API 29+ 动态（列表 minimal）/ Android 旧机 minimal。
- **新增硬约束**：guoapp 用 `dependency_overrides` 把 Windows 原生库指向自维护包 `1.0.11+duanju.1`，其 CMake 对 arm64 直接 `FATAL_ERROR`——Windows ARM64 在原生库层面即不支持。

PRD §3、ARCH §2/§4/§6/§8、EVIDENCE §16 已回写。

### Q10 ✅ LAN 同步/推送播放入不入 P1？

- **证据**：guoapp 0.2.13 已实现（mDNS+TLS1.3 mTLS+版本向量+删除标记+两阶段提交），但**真实双端未验证**；  
  协议成熟可抄，工作量约一个中型子系统，且依赖 nsd 包的平台覆盖（Win10 1903+/iOS 13+）。
- **选项**：a) P1 分支照抄协议；b) 只做"推送播放"不做同步；c) 整个砍掉（备份导入导出替代）。
- **建议**：c 或 b。聚合 App 的同步是 nice-to-have，备份+导出已覆盖 80% 场景；要做就从"推送播放"单点切入。

**✅ 已决（2026-10-14）：c，整个砍掉。** 同步与推送播放都不做；跨设备迁移由备份导入导出替代  
（Q14 的源清单建议因此更值钱）；EVIDENCE §11 留证备查，ARCH §7 移除 lan 分支。

### Q11 ✅ OHOS 分支什么时候开始调研？

- **证据**：主 SDK 出不了 OHOS 包；`media_kit` 无 ohos 适配，播放器要接原生；glass 按 minimal 验收。  
  若 P0 编码完成后才调研，分支永远追不上 main（FFI/播放/存储三处都分叉）。
- **选项**：a) M0 期间出调研 Spike（1 周：SDK 装通+hello FFI+原生播放 PoC）；b) P0 完全不管；c) 直接砍掉 OHOS。
- **建议**：a。Spike 结论（尤其是原生播放器接入成本）决定 OHOS 是 P1 还是永不。

**✅ 已决（2026-10-14）：完成 P0 发版再做。** M0 不出 Spike；P0 发版后集中调研  
（SDK 装通 + hello FFI + 原生播放 PoC），结论再定 P1 或永不。PRD §3、ARCH §7 已回写。

### Q12 ✅ iOS 到底进不进 P1 首批？

- **证据**：libmpv 渲染上下文失败 `exit(1)` 前车之鉴（guoapp 0.2.40 兜底后才敢发）；后台下载仅前台；  
  glass 全档可用但 Metal 路径未验。三平台里 iOS 的未知最多。
- **选项**：a) P1 首批（含真机计划）；b) P1 末位；c) 不做 iOS。
- **建议**：b。P0 三平台（Android/Win/macOS）稳定前不启动 iOS 真机工作。

**✅ 已决（2026-10-14）：b，P1 末位。** P0 三平台稳定前不启动 iOS 真机工作；  
media_kit `exit(1)` 兜底等风险预研不推迟、真机验证推迟。PRD §3、ARCH §7/§8 已回写。

## D. 合规与运营（拷问 PRD §4）

### Q13 ⬜ "违规源一键禁用+清缓存"——谁触发、按什么标准？

- **证据**：guoapp 的暮果移除是**用户人工判断**（成人站点+自带过滤未移植）；没有任何自动化审核。  
  我们是聚合平台+第三方源分发，没有运营侧定义就等于没有合规流程。
- **选项**：a) 定义流程（官方源上架审核 + 第三方源用户举报 + 健康检测异常自动降权）；b) 只做技术开关不定义流程。
- **建议**：a 至少落到文档：谁审、审什么（成人/侵权/盗链）、处置动作（禁用/清缓存/下架）、  
  用户协议里第三方源免责声明的位置。这条不关闭，SourceSpec §5 的"上架门槛"是空中楼阁。

### Q14 ⬜ 第三方源换机后要重新授权，接受吗？

- **证据**：kv 私域/凭证不进备份是安全设计（guoapp 同样）；代价是用户换机后第三方源全部要重新走  
  "URL/扫码/文件导入 + domains 授权"。
- **选项**：a) 接受（现状，安全优先）；b) 备份含源清单+授权记录（不含密钥），换机后一键重装。
- **建议**：b 的前半句可以给：备份含**已安装源清单与授权决定**（不含 kv/密钥），恢复后提示重装。  
  既保安全又降挫败感。需回改 PRD §6 备份条目。**Q10 砍掉 LAN 后，本条的优先级上升**（备份是跨设备迁移唯一通道）。

## E. 验证与交付（拷问 §8/§9）

### Q15 ⬜ P0 排期锚点是什么？

- **证据**：无。ARCH v0.1 完全没有里程碑；Rust target 只装了 x86_64-pc-windows-msvc。
- **选项**：a) 按 PRD §8 的 M0–M4 推进；b) 重新砍到"能演示的最小闭环"（红果目录+播放+一个官方源）。
- **建议**：a 保留但明确 M2（播放闭环）是**演示锚点**，M3/M4 是质量债。若时间紧，M3 下载可再砍（回 Q2——已决 a，不砍）。

### Q16 ⬜ "未验证快照"制度写进我们的流程吗？

- **证据**：guoapp 用 AGENTS.md + README 首行标注维持纪律（"0.2.55+61 未验证开发快照"、"历史检查不得沿用"）；  
  好处是复盘时每个数字有出处，坏处是文档负担。
- **选项**：a) 采纳（PRD §9 已预填）；b) 只在做版本快照时标注。
- **建议**：a。你的核验偏好（数字必须能从产物里查出来）和这个制度是同一件事。

### Q17 ⬜ 真机矩阵预算：1 台 ARM64 Android + Windows x64 + TV 焦点 + iOS 一台，够吗？

- **证据**：guoapp 的最小有效集就是这个（TV 用 overlay 先行、真机抽查）；画质增强的教训是  
  "桌面成立≠移动成立"，持续性能必须固定亮度/供电跑 20–30 分钟。
- **选项**：a) 按上述最小集；b) 加一台中低端 Android（Adreno/Mali 覆盖）。
- **建议**：a + "若 P1 做画质增强则必须加 b"。**Q12 已决 iOS P1 末位**，P0 真机集相应改为：  
  ARM64 Android + Windows x64 + macOS（premium 玻璃验收）+ Android API <29 旧机（legacy GL 路径）；iOS 真机推迟。

## Q24 🔴 红果源用什么形态实现？（**当前按 a 推进，待确认**）

- **背景**：红果需 X-Gorgon 签名 + Android 设备伪装 + spade_a→CENC 密钥派生 + AES-CBC 响应解密（EVIDENCE §17），  
  属必须代码实现的特权源。P0 只有它一个源。
- **选项**：
  - **a) Rust 引擎内置，实现 `SourceProvider` trait（当前采用）**——  
    最快出 MVP；trait 保证 P2 加扩展源时下游零改动；特权逻辑天然不出引擎。  
    代价：换源仍需改 Rust 代码（但这在"只有一个源"时不是问题）。
  - b) 红果也做成 WASM 插件，从第一天建 WASM 宿主（保持 v0.1"源逻辑 WASM 化，从第一天执行"的立场）——  
    多出 extism/wasmtime 宿主 + host 函数 + 凭证 API 的基建成本，且红果是特权源，宿主要为它开特权通道，收益为负。
  - c) 红果内置 + WASM 宿主同时做——工作量最大，P0 不需要。
- **建议**：**a**。`SourceProvider` trait 是"支持后续源扩展"的真实落点（不是纸面承诺）；  
  且 EVIDENCE §17.1 已证明红果不可规则化，b 的额外成本换不来 P0 收益。
- **⚠️ 连带**：选 a 意味着 v0.1 立场的"源逻辑 WASM 化，从第一天执行"**被修订为**  
  "源抽象 trait 化从第一天执行，WASM 宿主延后至 P2"。请在确认时一并认可此修订。

## Q25 🔴 第三方非授权客户端的免责声明与合规流程（Q13 在该定位下升级为必答）

- **背景**：v0.5 定位为**逆向红果私有协议的第三方客户端**（非官方授权），且内置 Android 设备伪装参数  
  （`device_type=25053RT47C`、`device_brand=Redmi` 等，EVIDENCE §17.1）。合规风险高于"聚合多源"的原定位。
- **需决断**：
  1. 免责声明放在哪几处？（建议：首次启动引导 + 关于页 + README 首屏，三处）
  2. 是否内置"24 小时内清除缓存数据"一类的自限条款？（kazumi 有此条款，可参照）
  3. 是否需要法务复核？由谁签？
  4. 设备伪装参数是否固定写死，还是运行时随机生成？（影响风控与合规双重风险）


- **建议**：1 按三处；2 暂不做（影响离线体验，且非法律要求）；3 M0 前必做；  
  4 **设备 ID（`device_id`/`iid`）运行时生成并持久化**（EVIDENCE §17.1 的 `newHongguoDeviceID` 即此做法），  
  但 `device_type`/`device_brand` 等型号字段按 guoapp 固定值。
- **⚠️ 优先级**：**建议 M0 前关闭**，不要拖到编码后期。

## Q26 源扩展延后后，`SourceProvider` trait 的能力面是否要按红果裁剪？

- **背景**：trait 现在按红果能力定义（catalog/search/suggest/detail/recommend/ranking/play）。

- **选项**：a) 维持全套 + `Caps` 位（未声明返回 `UNSUPPORTED`，当前采用）；  
  b) 只留 catalog/search/detail/play 四件套，recommend/ranking 走红果专属扩展接口。
- **建议**：**a**（`Caps` 机制已在 SourceSpec §11.1 定义，且"未声明能力返回 UNSUPPORTED 不返回空列表"是星果/河果教训）。

## Q27 🔴 取流是否采用「Web 免签优先 + App 签名兜底」双轨？（**当前按 a 推进**）

- **背景（联网调研 + 复核 guoapp 代码）**：红果取流存在三条路（EVIDENCE §17.4）：
  - **① 官网 SSR 免签** `hongguoduanju.com/player/{sid}/{vid}` → `_ROUTER_DATA` → `video_player_info` → **明文直链，零解密**，但**只覆盖可试看集**  
    （guoapp 自己的错误文案即写明"可能仅允许网页试看"、"不会将试看集冒充该集下载"）。
  - **② App API 签名** fqnovel `video_model` → **CENC**，覆盖**全集**，但要 X-Gorgon + 设备伪装 + spade_a 派生。
  - **③ 第三方中转** `djapi.999888456.xyz` ——  guoapp 的第三级兜底，**非官方域名**。
- **选项**：
  - **a) 双轨 ①+②，禁用 ③（当前采用）**：M0 只做 ①（免签明文，立刻跑通闭环），M1 接 ② 补非试看集。
  - b) 只做 ②（v0.5 原方案）：全集一步到位，但 M0 就被 CENC 卡住，存在"做不出来"的风险。
  - c) 只做 ①：最简单，但只能看试看集，**对"追剧 App"而言功能残缺**。
- **建议**：**a**。关键收益是**把 CENC 从 P0 阻断项降为 M1 增强项**——M0 不再有"做不出来"的风险。
- **⚠️ 连带确认**：是否接受"部分剧集初期只能看试看集"？建议接受，并在 UI 明示"该集需 App 授权"（而非静默失败）。

## Q28 🔴 M0 必验：X-Argus / X-Ladon 是否已成强制项？

- **背景**：guoapp 的**主 API 签名只设 X-Gorgon**（`provider_hongguo_sign.go:23-46`），  
  但其**弹幕签名同时设 X-Gorgon + X-Argus + X-Ladon**（`provider_hongguo_comment_sign.go:56-61`）。  
  而社区项目 `sgccdev/hongguo-web` 称其后端"**所有**官方 API 调用都需要 X-Argus/X-Gorgon 签名"，并另外提到 X-Ladon。  
  **guoapp 自 2026-09-21 起暂停集中验证**，其"只发 X-Gorgon"的做法**可能已失效**。
- **验证方式**：M0 用真机/模拟器抓包确认主 API（fqnovel）实际要求哪几个头。  
  开发期可用 frida hook 抓一批真实请求-签名样本，作为 Rust 实现的**离线向量单测**，运行时不依赖 frida。
- **建议**：M0 抓包确认后再定实现范围；**不要默认"照抄 guoapp 就一定还能用"**。

## Q29 是否接受用 frida 抓真实签名样本做单测向量（仅开发期，非运行时）？

- **背景**：社区下载器普遍用 frida hook 真机 App 当"签名预言机"（运行时依赖模拟器 + frida-server + 红果 App 常驻）。  
  **运行时这条路对终端 App 完全不可行**，但**开发期**用它抓取"真实请求 → 真实签名头"样本极有价值：  
  可离线校验我们的 Rust 实现是否正确，防止算法漂移或抄错变体。
- **建议**：**开发期用，运行时不用**。抓到的样本固化为单测向量提交进仓库（类似 guoapp 的固定响应样本做法 [G12]）。
- **⚠️ 前提**：需要一台安卓真机/模拟器 + frida 环境，属一次性投入。

## Q30 ⬜ 海报缓存用现成包还是自研 LRU？

- **背景**：guoapp 自研 `app_covers.go`，策略为 **30 天 / 256MiB / 2000 张** [G6]；ARCH §2.1 暂列 `cached_network_image` 或自研 LRU 二选一。
- **选项**：a) `cached_network_image`（省事，但缓存策略受限）；b) 自研 LRU（可精确复刻 guoapp 的 30 天/256MiB/2000 张三闸门）。
- **建议**：**待定**——需精确匹配 guoapp 驱逐策略则选 b，否则 a 足够。属 M1 前关闭的次要项。

## Q31 ⬜ 结构化存储 `drift` 与 `shared_preferences` 如何分工？

- **背景**：ARCH §2.1 引入 `drift` 替 guoapp 的"单 key 16MiB JSON 快照"，同时保留 `shared_preferences`，两者分工未定。
- **选项**：a) 追剧/历史/下载清单走 `drift`，设置类轻量键值走 `shared_preferences`；b) 全部走 `drift`。
- **建议**：**a**——结构化数据与轻量键值分离，避免把大 JSON 塞进 `shared_preferences`（guoapp 的老问题）。

## Q32 ✅ 状态管理与 DI 的选型（**已决 2026-10-15，用户：采用 Riverpod 3**）

- **决策**：状态管理与 DI 采用 **Riverpod 3** —— `flutter_riverpod` + 代码生成（`riverpod_annotation` / `riverpod_generator`），**替代 `provider` + `get_it`**（Riverpod 自身承担 DI）；**仍不引入 Bloc**。
- **落地方式**：ViewModel 以 Riverpod `Notifier` / `AsyncNotifier` 实现，经 `Provider` / `AsyncNotifierProvider` 暴露给 UI；`ref.watch` / `ref.read` 承担依赖注入，移除 `get_it` 的 service locator。
- **FFI**：ABI 仅 3 个符号，**采用 `ffigen` 生成**以保留符号对照单测（与 SourceSpec §11.1 trait 冻结联测）。
- **同步**：ARCH §1 架构图 / §2 技术栈表 / §2.1 包清单已按此更新；Riverpod 版本号待 M0 `pub add` 后锁定并回写 EVIDENCE §19。
